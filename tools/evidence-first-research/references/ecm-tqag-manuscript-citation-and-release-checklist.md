# ECM–TQAG Manuscript, Citation, and Release Checklist

## Manuscript structure and scientific meaning
- Contributions state **scientific methodological contributions**, not implementation tasks or evaluation activities. Map each contribution 1–1, in order, to a Methodology subsection that realizes it. Experimental sections only evaluate observable consequences of those methods.
- Abstract: problem/gap → method → evaluation approach → significance. Exclude detailed counts, model/provider names, seed, temperature, hashes, endpoint, prompt mechanics, and execution logs.
- Keywords use scientific field/method terms, never operational labels.
- Keep Introduction (gap/positioning/contributions), Method (method realization), Results (artifact-supported findings), Limitations (research gaps), and Conclusion (synthesis only) distinct. Avoid repeating tables or claims across them.

## Notation, figures, and table layout
- Use a single meaning per symbol throughout. Explicitly separate: document components; evidence-condition labels; source-level provenance mapping; item-level traces; and experimental trial sets.
- When explaining notation to Người dùng, provide a compact table: **symbol — meaning — English pronunciation**.
- Method figures explain the pipeline; result tables present measurements. Keep one authoritative table only. Prefer table floats at the beginning of the relevant Results page/section; inspect rendered PDF after float changes.

## Limitations and declarations
- Limitations must state meaningful scientific gaps: generalizability, external semantic/legal/pedagogical validation, distractor quality, and conditions under which visual modality is genuinely necessary. Do not put code, repositories, logs, hashes, or access restrictions here.
- Put data/code/material access, redistribution rights, and repositories in a separate Availability section.
- Keep Acknowledgment, Funding, Conflict of Interest, and AI disclosure short and functional. Do not invent facts. AI disclosure should only state the approved high-level uses (e.g., grammar assistance, code development, figure preparation), without provider/model details unless a venue requires them.

## Citation discipline
- Add citations because a specific claim needs grounding, not to inflate the bibliography. Typical claim families: document AI/VQA, educational and visual question generation, structured reasoning, provenance, MCQ item writing, reproducibility/auditing, and modality bias.
- Every citation must resolve to a valid BibTeX entry; remove unreferenced entries unless retained by an explicit venue rule.
- After citation edits: clean-build; check undefined citations/references; verify a 1–1 match between cited keys and bibliography entries; inspect bibliography page layout. If references add a page, first remove repeated prose rather than discarding necessary sources.

## Experimental prose boundary
- Describe the scientific design: evidence conditions, protocol definitions, controlled/paired comparisons, measurements, and the scope of conclusions.
- Do not put code/configuration prose in the main narrative: concrete model/provider names, API URLs, API keys, seeds, temperatures, endpoint mechanics, prompt plumbing, or statements such as “all conditions use …”. Keep required operational metadata in supplementary/provenance records only when the venue requires it.

## Clean LaTeX source package
1. Include only compile dependencies: main `.tex`, cited `.bib`, actually used figure/table assets, and a concise build README.
2. Exclude PDFs generated by build, `.aux`, `.bbl`, `.blg`, logs, caches, and unused assets.
3. Build the archive, unpack it in a new directory, and compile independently before delivery.

## Public research-software release boundary
- Never publish API keys/tokens, real provider endpoints, operational model identifiers, private outputs, source-derived restricted data, or unapproved images.
- Remote runs are opt-in: track only a non-routable template (for example `.invalid`), placeholders, and the **name** of an environment variable; ignore `.env`, local, and private config files.
- A research-software README should cover artifact scope, method/contracts, installation, offline reproduction, optional remote execution and security boundary, fixture/data governance, repository layout, citation, license, and explicit semantic-validation limits.
- Before public push: run targeted tests, build/package checks, deterministic release-boundary audit, and a diff/secrets review. Commit/push only when these pass.
